## 2. 設計思想：なぜサーバーコンポーネントファーストか

### 従来実装（Pages Router + SWR）との違い

教材のオリジナル実装では以下のようなパターンを使っていました:

```
// 従来パターン（Pages Router + SWR）
// クライアントで全データを取得し、グローバルステートで管理
const { data } = useSWR('/api/articles', fetcher);
const currentUser = useRecoilValue(currentUserAtom);
```

本実装ではこのパターンをすべてサーバーサイドに移動しました:

```tsx
// 新パターン（App Router + Server Components）
// サーバーで直接取得。クライアントJSなし
export default async function HomePage() {
  const res = await fetchApi('/articles', { cache: 'no-store' });
  const articles = toCamelCase(await res.json());
  return <ArticleList articles={articles} />;
}
```

### サーバーコンポーネントを選んだ理由

**1. APIトークンをブラウザに露出させない**

認証トークン（`access-token`, `uid`, `client`）はhttpOnly Cookieに保存されます。httpOnly CookieはJavaScriptから読み取れないため、XSS攻撃でトークンが盗まれるリスクがありません。サーバーコンポーネントはサーバー側でCookieを読み取るため、この設計と相性が良いです。

**2. ウォーターフォール問題を避けられる**

クライアントサイドでSWRを使うと「コンポーネントがマウントされてからfetchが走る」という遅延が発生します。サーバーコンポーネントならHTMLを返す時点でデータが揃っているため、ページ表示が速くなります。

**3. バンドルサイズの削減**

サーバーコンポーネントのコードはクライアントのJavaScriptバンドルに含まれません。SWR・axios・グローバルステートライブラリなどが不要になります。

**4. シンプルなデータフロー**

`fetch → data → render` という一方向の流れのみ。グローバルステート管理（Recoil、Jotai等）が不要になり、コードがシンプルになります。

### 4-2. APIクライアント `lib/api.ts`

```typescript
const API_BASE_URL = process.env.API_BASE_URL ?? 'http://rails:3000/api/v1';

export async function fetchApi(path: string, options: RequestInit = {}): Promise<Response> {
  const hasBody = options.body !== undefined;
  const headers: HeadersInit = {
    ...(hasBody ? { 'Content-Type': 'application/json' } : {}),
    ...options.headers,
  };
  return fetch(`${API_BASE_URL}${path}`, { ...options, headers });
}
```

**なぜ `API_BASE_URL` をサーバー専用にするか**

`process.env.API_BASE_URL`（`NEXT_PUBLIC_` プレフィックスなし）はサーバーサイドでのみ参照できます。本番環境ではDocker内部ネットワークで `http://rails:3000` に直接アクセスしており、ブラウザからは到達できないURLです。クライアントコンポーネントからは呼ばず、サーバーコンポーネント・サーバーアクションからのみ呼ぶ設計です。

**`Content-Type` の自動付与**

GETリクエストに `Content-Type: application/json` を付けると一部のRailsエンドポイントでエラーが発生します。`body` が存在する場合のみ付与するようにしています。

---

**snake_case → camelCase 変換 `toCamelCase`**

```typescript
type Json = string | number | boolean | null | Json[] | { [key: string]: Json };

function camelCaseKey(str: string): string {
  return str.replace(/_([a-z])/g, (_, char) => char.toUpperCase());
}

export function toCamelCase(obj: Json): Json {
  if (Array.isArray(obj)) return obj.map(toCamelCase);
  if (obj !== null && typeof obj === 'object') {
    return Object.fromEntries(
      Object.entries(obj).map(([key, value]) => [camelCaseKey(key), toCamelCase(value)]),
    );
  }
  return obj;
}
```

**なぜ camelcase-keys パッケージを使わないか**

外部パッケージを追加するより、わずか10行の自前実装の方がシンプルです。再帰的に処理するためネストしたオブジェクトも変換できます。`from_today` → `fromToday` のような変換が正しく行われます。

### 4-3. 認証ユーティリティ `lib/auth.ts`

```typescript
import { cookies } from 'next/headers';

export async function getAuthHeaders(): Promise<Record<string, string>> {
  const cookieStore = await cookies();
  return {
    'access-token': cookieStore.get('access-token')?.value ?? '',
    uid: cookieStore.get('uid')?.value ?? '',
    client: cookieStore.get('client')?.value ?? '',
  };
}

export async function getCurrentUser(): Promise<CurrentUser | null> {
  const cookieStore = await cookies();
  const uid = cookieStore.get('uid')?.value;
  if (!uid) return null;   // クッキーがなければ即returnで無駄なfetchを避ける

  try {
    const authHeaders = await getAuthHeaders();
    const res = await fetchApi('/current/user', {
      headers: authHeaders,
      cache: 'no-store',
    });
    if (!res.ok) return null;
    return await res.json() as CurrentUser;
  } catch {
    return null;
  }
}
```

**`cookies()` はサーバー専用API**

Next.jsの `next/headers` から提供される `cookies()` はサーバーコンポーネントとサーバーアクションの中でのみ呼び出せます。httpOnly Cookieを読み書きできるのがサーバーサイドのみという制約と一致しています。

**`cache: 'no-store'` の理由**

認証状態はリクエストごとに最新を確認する必要があります。`no-store` を指定しないとNext.jsがレスポンスをキャッシュしてしまい、サインアウト後も認証済みとして扱われる可能性があります。

## 5. サーバーアクション

サーバーアクションは `'use server'` ディレクティブを持つ非同期関数です。クライアントコンポーネントのフォームから呼び出せますが、実行はサーバー上で行われます。

### 5-1. 認証アクション `app/_actions/auth.ts`

#### signIn

```typescript
'use server';

const COOKIE_OPTIONS = {
  httpOnly: true,
  secure: process.env.NODE_ENV === 'production',
  sameSite: 'lax' as const,
  maxAge: 60 * 60 * 24 * 30,  // 30日
};

export async function signIn(_prevState: AuthState, formData: FormData): Promise<AuthState> {
  const email = formData.get('email') as string;
  const password = formData.get('password') as string;

  const res = await fetchApi('/auth/sign_in', {
    method: 'POST',
    body: JSON.stringify({ email, password }),
  });

  if (!res.ok) {
    return { error: 'メールアドレスまたはパスワードが正しくありません' };
  }

  // devise_token_auth はトークンをレスポンスヘッダーに入れて返す
  const cookieStore = await cookies();
  cookieStore.set('access-token', res.headers.get('access-token') ?? '', COOKIE_OPTIONS);
  cookieStore.set('uid', res.headers.get('uid') ?? '', COOKIE_OPTIONS);
  cookieStore.set('client', res.headers.get('client') ?? '', COOKIE_OPTIONS);

  redirect(`/?message=${encodeURIComponent('サインインしました')}&severity=success`);
}
```

**devise_token_auth との連携**

Rails側の `devise_token_auth` はトークンをレスポンスヘッダーに含めて返します:
- `access-token`: 毎リクエストごとにローテーションするアクセストークン
- `uid`: ユーザーを識別するメールアドレス
- `client`: セッションを識別するクライアントID

この3つをセットでCookieに保存し、以降のAPIリクエストに同じヘッダーとして付与することで認証が成立します。

**なぜlocalStorageではなくhttpOnly Cookieか**

| | localStorage | httpOnly Cookie |
| --- | --- | --- |
| JavaScriptからアクセス | ○（XSSで盗まれる危険） | ✗（JavaScriptから読めない） |
| サーバーコンポーネントで読める | ✗ | ○ |
| 有効期限の設定 | 手動管理が必要 | `maxAge` で自動管理 |
| CSRF対策 | 不要（Authorizationヘッダー） | `SameSite` で対応 |

教材のオリジナル実装はlocalStorageにトークンを保存していましたが、httpOnly Cookieの方がセキュリティが高く、サーバーコンポーネントで直接読めるため採用しました。

**`redirect()` の位置**

`redirect()` は `try-catch` の外で呼ぶ必要があります。内部的にはエラーをthrowして処理するため、`try-catch` 内に書くとcatchされてしまいます。本実装では成否フラグ変数を使ってtry-catchを抜けてからredirectしています。

#### signOut

```typescript
export async function signOut(): Promise<void> {
  const cookieStore = await cookies();
  // 1. Railsに無効化リクエスト（失敗してもサインアウトは続行）
  try {
    await fetchApi('/auth/sign_out', {
      method: 'DELETE',
      headers: { 'access-token': ..., uid: ..., client: ... },
    });
  } catch {
    // ローカルのCookie削除は必ず実行する
  }

  // 2. Cookieを削除
  cookieStore.delete('access-token');
  cookieStore.delete('uid');
  cookieStore.delete('client');

  redirect(`/?message=${encodeURIComponent('サインアウトしました')}&severity=success`);
}
```

ネットワークエラーでRailsへの無効化リクエストが失敗しても、ローカルのCookieを削除すればサインアウトとして機能します。

### 5-2. 記事アクション `app/_actions/articles.ts`

#### createArticle

```typescript
export async function createArticle(): Promise<void> {
  const authHeaders = await getAuthHeaders();
  let articleId: number | null = null;

  try {
    const res = await fetchApi('/current/articles', {
      method: 'POST',
      headers: authHeaders,
      body: JSON.stringify({ article: { title: '', status: 'draft', content: '' } }),
    });
    if (res.ok) {
      articleId = (await res.json()).id;
    }
  } catch { /* エラーは以下のredirectで処理 */ }

  if (articleId) {
    redirect(`/current/articles/${articleId}/edit`);
  } else {
    redirect(`/current/articles?message=...&severity=error`);
  }
}
```

「新規記事」ボタンを押すと空の記事をDBに作成し、即座に編集画面にリダイレクトします。この設計により「記事の保存」と「編集開始」が分離され、ユーザーが途中でページを離れても下書きが残ります。

#### updateArticle とバインドパターン

```typescript
export async function updateArticle(
  id: number,           // ← バインドされる引数（フォームの外から渡す）
  _prevState: ArticleState,
  formData: FormData,
): Promise<ArticleState>
```

`useActionState` はアクション関数のシグネチャを `(prevState, formData) => Promise<State>` と期待しています。しかし記事IDをフォームデータとは別に渡したい場合、`Function.prototype.bind` で引数を部分適用できます:

```typescript
// ArticleEditForm.tsx（クライアントコンポーネント）
const boundAction = updateArticle.bind(null, article.id);
// → (prevState, formData) => Promise<State> と同じシグネチャになる
const [state, formAction, isPending] = useActionState(boundAction, null);
```

このパターンを使うことで、コンポーネント内の `useState` や `useRef` でIDを管理する必要がなくなります。

## 6. コンポーネント設計

### SC/CC の分割基準

```
サーバーコンポーネント（デフォルト）
  ✓ データフェッチが必要
  ✓ CookieやAuthヘッダーが必要
  ✓ useState/useEffectが不要
  ✓ ブラウザAPIが不要

クライアントコンポーネント（'use client'が必要）
  ✓ useState / useReducer が必要
  ✓ useEffect が必要
  ✓ useRouter / useSearchParams / usePathname が必要
  ✓ イベントハンドラ（onClick等）が必要
  ✓ ブラウザAPIが必要
```

### 6-1. Header `app/_components/Header.tsx`（CC）

```tsx
'use client';

type Props = { currentUser: CurrentUser | null };

export default function Header({ currentUser }: Props) {
  const [anchorEl, setAnchorEl] = useState<null | HTMLElement>(null);

  return (
    <AppBar>
      {currentUser ? (
        <>
          {/* 新規記事ボタン：サーバーアクションを直接form actionに */}
          <form action={createArticle}>
            <Button type="submit">新規記事</Button>
          </form>

          {/* アバターメニュー */}
          <IconButton onClick={(e) => setAnchorEl(e.currentTarget)}>
            <Avatar />
          </IconButton>
          <Menu anchorEl={anchorEl}>
            <form action={signOut} style={{ display: 'contents' }}>
              <MenuItem component="button" type="submit">サインアウト</MenuItem>
            </form>
          </Menu>
        </>
      ) : (
        /* サインイン・サインアップボタン */
      )}
    </AppBar>
  );
}
```

**なぜHeaderはクライアントコンポーネントか**

ドロップダウンメニューの開閉に `useState` が必要なため `'use client'` にしています。ただし `currentUser` はRootLayout（サーバーコンポーネント）で取得してpropsとして渡しています。「データ取得はサーバー、インタラクションはクライアント」という分離を実現しています。

**`form action` にサーバーアクションを直接渡す**

React 19では `<form action={serverAction}>` が使えます。これはJavaScriptなしでも動作するプログレッシブエンハンスメントです（`fetch` を使うSWRとの大きな違い）。

### 6-2. Snackbar `app/_components/Snackbar.tsx`（CC）

```tsx
'use client';

export default function Snackbar() {
  const searchParams = useSearchParams();
  const pathname = usePathname();
  const router = useRouter();
  const [open, setOpen] = useState(false);
  const [message, setMessage] = useState('');

  useEffect(() => {
    const msg = searchParams.get('message');
    if (msg) {
      setMessage(msg);
      setOpen(true);
    }
  }, [searchParams]);

  const handleClose = () => {
    setOpen(false);
    // URLからmessageパラメータを削除（履歴を残さないreplace）
    const params = new URLSearchParams(searchParams.toString());
    params.delete('message');
    params.delete('severity');
    router.replace(params.toString() ? `${pathname}?${params}` : pathname);
  };
  // ...
}
```

**URLサーチパラメータによる通知パターン**

サーバーアクション完了後の通知をどう実現するかが設計上の課題です。選択肢:

| 方法 | 問題点 |
| --- | --- |
| グローバルstate（Jotai等） | サーバーコンポーネントでは使えない |
| LocalStorage | サーバーコンポーネントでは読めない |
| URL searchParams | ✓ サーバーアクションの `redirect()` で付与できる |

サーバーアクション内で `redirect('/?message=サインインしました&severity=success')` とするだけでSnackbarが表示されます。通知を表示後は `router.replace()` でURLからパラメータを消します。

**なぜ `<Suspense>` で囲むか**

`useSearchParams()` はReactのサスペンス境界を必要とします。これを `<Suspense fallback={null}>` で囲まないとNext.jsのビルド時にエラーになります。

```tsx
// app/layout.tsx
<Suspense fallback={null}>
  <Snackbar />
</Suspense>
```

### 6-4. MarkdownText `app/_components/MarkdownText.tsx`（CC）

```tsx
'use client';

import ReactMarkdown from 'react-markdown';

export default function MarkdownText({ content }: { content: string }) {
  return (
    <Box sx={{
      '& h1': { fontSize: '1.75rem', fontWeight: 'bold' },
      '& h2': { ... },
      '& code': { bgcolor: 'grey.100', fontFamily: 'monospace' },
      '& pre': { bgcolor: '#282c34', color: '#abb2bf' },
      // ...
    }}>
      <ReactMarkdown>{content}</ReactMarkdown>
    </Box>
  );
}
```

**なぜクライアントコンポーネントか**

`react-markdown` はブラウザのDOM操作を前提としたライブラリのため `'use client'` が必要です。ただし、Next.jsはクライアントコンポーネントも初回ロード時にサーバーでHTMLをレンダリング（SSR）するため、SEOやパフォーマンスへの影響は最小限です。

**MUI の `sx` prop でMarkdownスタイリング**

Markdownがレンダリングする `<h1>`, `<h2>`, `<code>`, `<pre>`, `<blockquote>` などのHTML要素に対して、`sx` の子セレクタ（`'& h1': { ... }`）でスタイルを当てています。CSSクラスを管理せずにMUIのテーマシステムと統合できます。

### 7-2. ホームページ `app/page.tsx`（記事一覧）

```tsx
export default async function HomePage() {
```

### 7-4. 記事詳細ページ `app/articles/[id]/page.tsx`

```tsx
type Props = {
  params: Promise<{ id: string }>;  // ← Next.js 15以降は非同期

export default async function ArticleDetailPage({ params }: Props) {
  const { id } = await params;     // ← await が必要

  const article = toCamelCase(await res.json()) as Article;
  return (/* ... */);

```

**Next.js 15以降の `params` は非同期**

Next.js 15から `params` がPromiseになりました。`await params` が必要です。これはNext.js 14以前のコードと非互換なので注意が必要です。

**`notFound()` の使い方**

存在しない記事IDにアクセスした場合は `notFound()` を呼びます。これはNext.jsが404ページを表示する組み込みの仕組みで、`app/not-found.tsx` をカスタマイズできます。

### 7-5. 記事編集ページ

**サーバーとクライアントの分割パターン**

```
app/current/articles/[id]/edit/
├── page.tsx                    ← サーバーコンポーネント（データ取得）
└── _components/
    └── ArticleEditForm.tsx     ← クライアントコンポーネント（インタラクション）
```

```tsx
// page.tsx（SC）：データを取得してCCにpropsで渡す
export default async function ArticleEditPage({ params }) {
  const { id } = await params;
  const authHeaders = await getAuthHeaders();
  const res = await fetchApi(`/current/articles/${id}`, { headers: authHeaders });
  const article = toCamelCase(await res.json()) as CurrentArticle;
  return <ArticleEditForm article={article} />;   // ← propsで渡す
}
```

```tsx
// ArticleEditForm.tsx（CC）：フォーム操作のみを担当
'use client';

export default function ArticleEditForm({ article }: { article: CurrentArticle }) {
  const [title, setTitle] = useState(article.title);
  const [content, setContent] = useState(article.content);
  const [showPreview, setShowPreview] = useState(false);

  // idをバインドしてuseActionStateに渡す
  const boundAction = updateArticle.bind(null, article.id);
  const [state, formAction, isPending] = useActionState(boundAction, null);

  return (
    <form action={formAction}>
      <TextField name="title" value={title} onChange={(e) => setTitle(e.target.value)} />

      {showPreview
        ? <MarkdownText content={content} />      // プレビュー表示
        : <TextField name="content" value={content} ... />  // 編集モード
      }

      {/* プレビュー中はhidden inputでcontentを送信 */}
      {showPreview && <input type="hidden" name="content" value={content} />}

      {/* status はSwitchで変更し、hidden inputで送信 */}
      <input type="hidden" name="status" value={isPublished ? 'published' : 'draft'} />
    </form>
  );
}
```

**プレビューモード時のhidden input**

プレビュー表示中はMarkdownTextコンポーネントが表示され、Textfieldは非表示になります。このとき `name="content"` のTextfieldがDOMに存在しないため、フォーム送信時にcontentが空になってしまいます。これを防ぐため、プレビュー中は `<input type="hidden" name="content" value={content} />` でcontentを送信しています。

## 8. 認証フロー全体

```
[サインインフォーム入力]
       ↓
[signIn Server Action]
  ・fetchApi('/auth/sign_in') → Railsへ
  ・Railsがレスポンスヘッダーに access-token, uid, client を返す
  ・cookies().set() でhttpOnly Cookieに保存
  ・redirect('/?message=サインインしました')
       ↓
[RootLayout が再レンダリング]
  ・getCurrentUser() → cookieを読んでAPIで認証確認
  ・currentUser を Header に渡す
  ・Header が「新規記事」ボタンとアバターを表示

[次回以降のAPIリクエスト（認証必要なページ）]
  ・getAuthHeaders() → cookies() から access-token, uid, client を取得
  ・fetchApi() のヘッダーに付与して送信
```

## 9. `useActionState` の使い方

React 19で安定版になった `useActionState` は、フォームとサーバーアクションを接続するためのhookです:

```tsx
const [state, formAction, isPending] = useActionState(
  serverAction,   // サーバーアクション（prevState, formData）=> State
  null,           // 初期state
);
```

| 戻り値 | 型 | 説明 |
| --- | --- | --- |
| `state` | `State \| null` | アクションが返した値（エラーメッセージ等） |
| `formAction` | `function` | `<form action={formAction}>` に渡す |
| `isPending` | `boolean` | 送信中は `true`（ボタン無効化に使う） |

```tsx
// サインインフォームの使用例
const [state, formAction, isPending] = useActionState(signIn, null);

return (
  <form action={formAction}>
    {state?.error && <Alert severity="error">{state.error}</Alert>}
    <TextField name="email" />
    <TextField name="password" type="password" />
    <Button type="submit" disabled={isPending}>
      {isPending ? 'サインイン中...' : 'サインイン'}
    </Button>
  </form>
);
```

## 10. 主要な設計判断まとめ

| 判断 | 選択 | 理由 |
| --- | --- | --- |
| データフェッチ | Server Components の `fetch` | クライアントJSが不要、バンドルサイズ削減 |
| 認証トークン管理 | httpOnly Cookie | XSSによるトークン盗難リスクがない、サーバーで直接読める |
| フォーム処理 | Server Actions + `useActionState` | Progressive Enhancement、追加ライブラリ不要 |
| グローバルstate | なし（props渡し） | シンプルなデータフロー、Recoil/Jotai不要 |
| APIクライアント | 自前の `fetchApi` ラッパー | axios不要、SWRのクライアントfetch不要 |
| マークダウン | react-markdown | SSR対応、React Componentとして統合しやすい |
| snake→camelCase | 自前の `toCamelCase` | 依存パッケージ追加なし、10行で完結 |
| 通知（Snackbar） | URL searchParams | サーバーアクションのredirectと相性が良い |
| ルート保護 | `layout.tsx` 内で `getCurrentUser()` | Middlewareより実装がシンプル |
